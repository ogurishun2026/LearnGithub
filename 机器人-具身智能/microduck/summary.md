# Microduck 研究总结

> 仓库地址：https://github.com/pollen-robotics/microduck
> 研究日期：2026-08-30

## 一、仓库概述

**一句话定位**：Microduck 是 Pollen Robotics 开源的微型双足机器人运行时——在 RK3566 ARM Linux 主板上，以 50 Hz 控制循环执行强化学习策略，并把电机安全、蓝牙、手柄、摄像头、深度传感器、声音、签名更新和自动回滚整合成一套多进程机器人系统。

它不是单独的强化学习 Demo，也不是完整的机械硬件开源仓库。这个仓库主要是“鸭子的脑和运维系统”：

- 机器人约 25 cm、800 g；
- Radxa Zero 3W / Rockchip RK3566；
- 15 个 Dynamixel 舵机和 IMU 共用一条 UART 总线；
- 强化学习策略以 ONNX 形式在板端推理；
- Rust workspace 中的多个 systemd daemon 分别管理运动、配置、更新、蓝牙、手柄、媒体和 ToF；
- 策略训练位于独立的 `microduck_rl` 仓库。

当前版本已经能在真机完成行走、站立、坐下、拾取、踢球、前滚翻、轮式移动、跌倒软着陆与重新站起，也具备局域网视频、声音和简单感知能力。但手机 App、SDK、互联网远程访问和自主行为“大脑”仍未完成。

## 二、整体架构

Microduck 没有把所有能力塞进一个大进程，而是拆成多个职责单一的 Linux 服务：

```text
gamepad       phone/BLE       robotctl/SSH       browser/WebRTC
   │              │                │                    │
 padd            btd           local sockets          mediad
   └──────────────┴────────────────┴────────────────────┘
                    JSON-RPC 2.0 / NDJSON
                       Unix domain sockets
                              │
             ┌────────────────┼────────────────┐
             ▼                ▼                ▼
          robotd           configd          updaterd
       control/safety   wifi/identity     update/rollback
             │
       15 servos + IMU

 tofd: 8x8 depth sensor       mediad: camera/audio/perception
```

### 2.1 服务职责

| 服务 | 负责内容 | 关键边界 |
|------|----------|----------|
| `robotd` | 50 Hz 控制循环、策略推理、关节、IMU、安全、里程计、声音 | 唯一可以触碰电机总线的服务 |
| `configd` | Wi-Fi、机器人身份、配对 PIN、手柄配对、重启 | `robotd` 挂掉后仍可工作 |
| `updaterd` | 下载、验签、安装、健康门禁、回滚 | 独立于 ML 和媒体栈 |
| `btd` | BLE GATT 到内部 API 的转发 | 只做传输，不拥有机器人状态 |
| `padd` | 手柄输入转换成运动意图 | 普通 socket 客户端，无电机权限 |
| `mediad` | 摄像头、麦克风、WebRTC、视觉检测和浏览器控制台 | 媒体崩溃不影响运动控制 |
| `tofd` | VL53L5/8CX 的 8x8 深度矩阵 | 只发布传感器数据，不读取其他服务 |
| `robotctl` | 本机运维 CLI | 即使 `robotd` 损坏也要可用 |

### 2.2 四条重要不变量

1. **运动安全只有一个写入口**：`robotd` 内部的 `Safety` 持有唯一 `RobotIo` 写句柄，策略和网络客户端无法绕过它直接控制舵机。
2. **恢复链路不依赖运动进程**：`configd`、`updaterd` 和 `btd` 在 `robotd` 无法启动时仍可配网、更新和回滚。
3. **控制循环不阻塞等待其他服务**：跨服务信息使用缓存或异步消息，不能拖住 50 Hz 热路径。
4. **每类状态只有一个所有者**：传输层只转发“意图”，不复制状态或私自决定行为。

这套架构的核心不是微服务数量，而是把“运动权力”和“故障恢复权力”隔开。

## 三、强化学习运动控制

### 3.1 统一的 61→14 策略接口

当前 alpha 机器人全部使用相同网络形状：

```text
obs[1,61] -> ONNX policy -> actions[1,14]
```

61 维观测包含：

| 范围 | 内容 |
|------|------|
| 0..3 | 陀螺仪角速度 |
| 3..6 | 投影重力方向 |
| 6..20 | 14 个关节相对 Home Pose 的位置 |
| 20..34 | 14 个关节速度 |
| 34..48 | 上一步策略动作 |
| 48..61 | 速度、头部和身体姿态命令 |

机器人有 15 个舵机，但嘴巴不参与策略，因此输出只有 14 维。观测和动作都通过同一份关节映射跳过嘴部，避免后半段关节发生静默错位。

### 3.2 随仓库发布的策略

仓库当前提供 9 个约 0.76 MB 的 ONNX 运动策略：

- walking；
- standing；
- sit/stand；
- ground pick；
- left/right ball kick；
- roller locomotion；
- roller crouch；
- forward roll / roulade。

这些策略来自早期 `microduck_runtime`，角色名与具体训练 run 分离，配置引用的是 `walk`、`stand` 等稳定槽位，而不是某次训练文件名。长期计划是将策略独立发布到 Hugging Face Hub，使步态更新不必重新发布整个 daemon。

### 3.3 50 Hz 控制循环

控制循环每 20 ms 执行一次，大致流程为：

```text
读取舵机 + IMU
  -> 更新跌倒/健康状态
  -> 合并最新控制意图
  -> 构造 61 维观测
  -> 选择 walking/standing/skill policy
  -> ONNX 推理
  -> 动作缩放和滤波
  -> Safety 检查
  -> 批量写入 15 个舵机
```

Ticker 采用 `Skip` 策略：错过周期时跳过旧 tick，而不是连续补发积压命令，也不让每次调度抖动永久累积。作者记录在真机非实时内核上曾达到约 50.0 Hz，15022 个 tick 中错过 3 次；这是项目方测量记录，本次没有真机复现。

## 四、安全控制设计

### 4.1 已落地的安全层

`duck-control/src/safety.rs` 将以下规则放在唯一电机写入路径上：

- `NaN` 和无穷值直接拒绝，保持当前姿态；
- 超出执行器范围的目标被限制到 `-π..π`；
- 500 ms 未收到新运动意图时，速度自动归零；
- 通信中断时停止行走但继续站立，而不是直接松力摔倒；
- 跌倒预测触发后降低舵机增益，软着陆，再缓慢回到站立姿态；
- 电池电压持续降至空电阈值时，先坐下再关机；
- ONNX Runtime 缺失、版本不兼容或内部 panic 会转为可诊断错误，控制循环保持姿态并继续报告健康状态。

其中“唯一写句柄”由 Rust 所有权约束，而不只是团队约定，这一点非常值得借鉴。

### 4.2 仍然存在的运动风险

当前角度限制是 XL330 舵机统一的一圈行程，**不是每个关节的机械/解剖限制**。它可以拦截非数值和离谱输出，但无法阻止一个数值有限、形状正确、却把膝盖或颈部推向机械危险位置的坏策略。

因此第三方策略即使通过 `obs[1,61] -> actions[1,14]` 形状检查，也不能直接视为安全。进入开放模型生态前，仍需要：

- 每关节位置/速度/加速度限制；
- 策略来源与签名分级；
- 台架验证和低增益试运行；
- 明确的物理急停与安全空间。

## 五、更新、验签和恢复

这是该仓库最成熟的部分之一。

### 5.1 发布链路

```text
GitHub Release
  -> 验证 manifest Minisign 签名
  -> 核对 artifact SHA-256
  -> 再验证 artifact 签名
  -> 限制解压文件数和总大小
  -> 安装到 releases/<version>/
  -> 原子切换 current symlink
  -> 重启相关 systemd 服务
  -> 调用真实 robot.health
       ├─ healthy/degraded: 提交更新
       └─ unhealthy: 自动切回上一版本
```

`updaterd` 支持多把正式公钥轮换，开发公钥以 `.dev.pub` 区分；客户配置默认不接受开发签名。更新日志与关键状态使用持久化目录保存，使回滚不依赖易失的 journal。

### 5.2 健康门禁的价值

它判断的不只是“进程有没有启动”，还会检查：

- 实际控制循环频率是否达到阈值；
- 控制循环是否已经长时间没有完成 tick；
- 连续电机总线读取错误是否超限；
- 需要的策略是否成功加载。

这避免了“服务显示 running，但机器人已经以错误频率运行”的假健康状态。

### 5.3 边界

- 更新器负责 Microduck 应用发布，不负责 OS、内核和外围固件 OTA；
- recovery net 已实现并随发布安装，但路线图明确记录：尚未用一个真正无法启动 daemon 的坏版本在真机完整演练；
- 签名保证发布来源，不等于发布内容没有逻辑缺陷，因此健康门禁和回滚仍然必要。

## 六、感知、媒体和交互

### 6.1 已有能力

- 手柄通过 `padd` 转成与 App 相同的运动意图；
- `duckctl` 可在没有 Wi-Fi 和 SSH 时通过 BLE 操作机器人；
- `mediad` 通过 GStreamer 和 RK3566 硬件 H.264 编码提供局域网 WebRTC；
- WebRTC data channel 使用与本地完全相同的 JSON-RPC API；
- `tofd` 以约 15 Hz 发布 8x8 ToF 深度矩阵；
- `pet-detect` 使用约 20 KB CNN 从麦克风判断是否正在被摸头；
- `duck-detect` 使用 RKNN NPU 或 ONNX CPU 模型识别画面中的其他 Microduck；
- 多只机器人可以通过 BLE 共享节拍并进行合唱；
- 合成声音、嘴部动作和 ToF theremin 已集成进 `robotd`。

### 6.2 真机性能取舍

视觉检测没有无上限运行，而是默认按约 2 Hz 取样。作者记录全速运行会令 Radxa Zero 3 达到 95°C，CPU 降频至 408 MHz，影响行走稳定性。

图像预处理也针对板端优化：检测器直接从 UYVY 摄像头帧抽样到 320x320 RGB，并在同一遍处理里完成旋转和 letterbox，避免先转换完整 720x1280 画面再缩小。

### 6.3 尚未完成

- 手机 App；
- Python SDK；
- 互联网外部的 rendezvous/TURN 远程访问；
- 每次摄像头会话的用户同意；
- 硬件摄像头指示灯；
- 完整自主行为系统。

目前的“智能”主要是 RL 动作策略和若干显式模式，不是一个能够长期自主决策的具身 Agent。

## 七、网络与隐私风险

这是当前版本最需要警惕的部分。

### 7.1 BLE 默认不安全

`btd --require-pairing` 默认关闭。项目这样选择是因为 macOS/BlueZ 的配对链路仍存在可用性问题，但实际后果非常直接：

- 附近的人可能读取传输中的配对 PIN；
- `net.connect` 中的 Wi-Fi 密码可能以明文经过无线链路；
- 工厂默认 PIN 是公开的 `000000`；
- 该配置只适合开发台架，不能直接交付用户。

项目代码会在每次启动时输出醒目警告，说明作者没有隐藏风险，但风险本身仍然存在。

### 7.2 局域网 WebRTC 不认证

`mediad` 默认监听 `0.0.0.0:8443`，机器人控制台在 `:8080`。当前没有机器人侧认证：同一网络内能访问 signalling 端口的人可以查看摄像头并发送运动命令。

它只适合可信实验网络，不能：

- 直接暴露到公网；
- 在不可信 Wi-Fi 中运行；
- 未增加防火墙、认证和会话同意就部署到家庭环境。

### 7.3 量产前必须补齐

1. 每台机器人唯一的工厂 PIN 或更强设备身份；
2. BLE 强制加密并完成 iOS/Android 真机验证；
3. WebRTC 会话认证和明确授权；
4. 摄像头/麦克风可见状态指示；
5. 默认防火墙和禁止公网端口转发；
6. 丢失凭据后的物理恢复流程。

## 八、工程质量与复现状态

### 8.1 工程证据

- 单一 Rust workspace，19 个 crate，职责边界清晰；
- GitHub Actions 执行 `fmt`、Clippy、workspace tests；
- 使用原生 ARM64 runner 验证 aarch64 构建与板级脚本；
- `board-test.sh` 覆盖回滚、篡改拒绝、boot counter、socket 权限和 peer credential；
- 更新器测试会注入坏签名、坏 hook、不健康版本和掉电窗口等故障；
- API 路由使用穷尽匹配，新增 RPC 方法时各传输层必须显式决定允许或拒绝；
- 文档不仅描述成功路径，也记录真机踩坑、未完成项和设计债务。

项目文档声明 macOS 下有 942 项测试通过，并且从 0.2.0 开始的每个版本都通过正式更新链路进入过真机。这些是作者记录，不是本次独立复现结论。

### 8.2 本次验证

本次完成了：

- 克隆并静态阅读主要源码、架构文档和路线图；
- `cargo metadata --no-deps` 成功解析全部 19 个 workspace package；
- `cargo fmt --all --check` 通过；
- 检查 CI、模型资产、提交历史和主要安全路径。

没有完成：

- 无 Microduck 真机，未验证舵机、IMU、NPU、摄像头、蓝牙和更新回滚；
- 完整 Rust 测试首次运行需要下载锁定依赖，本机网络未完成 `clap_derive 4.6.4` 获取，因此不能声称 942 项测试已在本机通过；
- 没有运行 RL benchmark 或验证策略动作质量。

### 8.3 开源边界

仓库包含机器人运行软件、部署配置和已导出的模型，但不等于完整整机复刻包：

- 没有在该仓库中发现完整机械 CAD 和 PCB 设计；
- RL 训练代码位于独立 `microduck_rl`；
- 训练录音和视觉数据集没有随仓库提供；
- 部分驱动和模型有各自来源与许可证，需要单独审查再分发。

## 九、学习价值

Microduck 最值得借鉴的不是“用 PPO 让机器人走起来”这一点，而是下面这些工程决策：

1. **神经策略不直接获得硬件写权限**：RL 输出必须通过普通控制和 Safety 层。
2. **恢复面与功能面分离**：运动程序坏掉不应同时摧毁配网和回滚能力。
3. **健康门禁使用真实业务指标**：进程存活不等于 50 Hz 控制循环健康。
4. **发布是原子替换而非在线打补丁**：签名、版本目录、软链接、健康检查、回滚形成闭环。
5. **同一 API 服务多种控制端**：手柄、BLE、CLI 和 WebRTC 最终发送相同意图，避免行为分叉。
6. **感知任务不能破坏运动时序**：媒体和 NPU 独立进程，检测频率服从温度和控制预算。
7. **把真实失败记录进设计文档**：硬件系统中，测量与故障历史往往比理想架构图更有价值。

对具身 Agent 项目而言，它提供了一个很好的参考分层：

```text
自主决策/LLM（尚未完成）
        ↓ intent
技能与 RL policy
        ↓ targets
确定性 Safety authority
        ↓ bounded command
硬件 IO
```

如果未来接入 LLM 或自主大脑，应该让其停留在“意图和技能选择”层，不能让生成式模型直接获得舵机总线写权限。

## 十、最终判断

| 维度 | 评价 |
|------|------|
| 机器人软件架构 | 9/10 |
| 强化学习落地工程 | 8/10 |
| 更新与故障恢复 | 9/10 |
| 测试和文档 | 9/10 |
| 开源复刻完整度 | 7/10 |
| 网络与隐私安全 | 3/10 |
| 当前消费级可用性 | 5/10 |
| 学习价值 | 9/10 |

**最终结论**：Microduck 已经超出研究 Demo，核心运动、服务拆分、发布和回滚具有明显的真实产品工程深度。它最有价值的地方是展示了如何把不完全可信的神经网络策略包进确定性安全层和可恢复运维系统。但当前仍是预量产阶段：默认 BLE 明文、局域网 WebRTC 无认证、工厂 PIN 固定、隐私同意和真机灾难恢复未闭环。在这些问题解决前，适合可信实验室研究和受控开发，不适合直接进入家庭或公网环境。
