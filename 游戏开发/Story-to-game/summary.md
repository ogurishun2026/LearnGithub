## 一、仓库概述

**一句话定位**：一个面向小说/剧本作者的「叙事文本 → 分支剧情游戏」全链路工具包，由一个 AI 改写技能 + 一个零依赖 HTML 游戏启动器组成。

**核心价值**：
- 作者只需向 AI 投喂线性叙事原文（短篇/中篇/长篇/剧本/大纲），即可产出可游玩的分支剧情 JSON 文件。
- JSON 文件用单页 HTML 启动器加载即可在浏览器内游玩，无需任何后端或依赖。
- 强调"**保留原作气质 + 选择必有回响**"的创作哲学，不是把小说切碎成填空题。

**面向人群**：
- 想把自己作品改成互动文游的小说/剧本作者
- 试图用 AI 做严肃叙事改编的研究者
- 寻找轻量级互动小说运行时的独立开发者

## 三、技术架构

### 3.1 story-to-game.skill（AI 技能包）

文件本质是 **ZIP 压缩包**，解压后结构：

```
story-to-game/
├── SKILL.md                          # 主工作流（九步铁律）
├── references/
│   ├── json-format-spec.md           # JSON 格式速查
│   ├── step1-ingestion.md            # 原作摄入与记忆索引（21KB，最详细）
│   ├── step2-style.md                # 风格指纹提取
│   ├── step3-structure.md            # 结构拆解与分支设计
│   ├── step4-system.md               # 状态系统与结局矩阵
│   ├── step5-writing.md              # 分段写作（55KB，体量最大）
│   └── step6-validation.md           # 验证与输出
└── scripts/
    └── validate.py                   # 13+ 项自动验证脚本
```

#### 九步工作流（铁律）

| 步骤 | 名称 | 关键产出 |
|------|------|----------|
| 1 | 原作摄入与记忆索引构建 | 骨架/人物/场景/文体 四层索引 + 节奏曲线 |
| 2 | 风格指纹提取 | 叙述温度/对白风格/节奏型/视角/原作禁区 |
| **✋ 确认点 A** | **方向对齐**（唯一必须等用户确认的环节） | 章节划分 / 玩家视角 / 核心张力 / 结局方向 |
| 3 | 结构拆解与分支点识别 | 节拍序列 + 分支拓扑 + 分支文学大纲 |
| 4 | 状态系统与结局矩阵设计 | val 定义 + variables + flags + 结局矩阵 |
| ✋ 确认点 B（可选） | 系统确认 | variableName 含义 + 结局/成就数量 |
| 5-7 | 分段写作 | 按章节推进的节点 JSON |
| 8 | 连通性验证与 JSON 输出 | 通过 validate.py 验收 |

#### 高度独特的"反 AI 偷懒"设计
- **步骤强制执行铁律**：即使用户喊"直接开始写"也必须先做规划。原因：跳过规划，质量"断崖式下降"。
- **反压缩铁律**：任何承载信息的内容禁止省略。明令禁止"用'他们聊了一会儿'概括完整对话""用'几天后'跳过有描写的时间段"。
- **分批输出协议**：节点数 >100 或原文 >3000 字必须分批，每批 50-100 节点，"宁可分多次对话完整输出，也不压缩内容塞进一次"。
- **断点存档 + 记忆重建**：跨对话续写时强制输出状态快照，新会话执行五步记忆重建。

### 3.2 JSON 剧本格式（核心 Schema）

```json
{
  "meta": { "title", "variableName", "initialVariable", "ambient", "cover": {...} },
  "startNodeId": "start",
  "variables": { "letterOpened": false, ... },
  "achievements": { "id": {"title", "description"} },
  "nodes": {
    "node_id": {
      "chapterTitle": "第一章",
      "title": "场景标题",
      "scene": { "id", "name", "type": "major|transient", "description", "arrival" },
      "progress": 40,
      "ambient": "rain|wind|tide|heat|static|...",
      "segments": [
        { "speaker": "系统", "text": "...", "effect": "breath" }
      ],
      "choices": [
        {
          "text": "拆开信封",
          "next": "open_letter",
          "condition": "val >= 60 | hasFlag '...' | {all|any|not}",
          "changes": {
            "val": 12,                       // 主状态值增减（0-100）
            "valSet": 50,                    // 直接赋值
            "set": { "letterOpened": true }, // 自定义变量赋值
            "addFlag": "checked_envelope",
            "importantFlag": {"id": "opened_letter", "label": "拆开信封"},
            "unlockAchievement": "first_choice"
          }
        }
      ],
      "routes": [
        { "condition": {...}, "next": "ending_true" },
        { "condition": "default", "next": "ending_quiet" }
      ],
      "next": "auto_jump_node",
      "isEnding": true,
      "type": "TRUE ENDING|NORMAL ENDING|BRANCH ENDING|RASH ENDING|HIDDEN ENDING|SPECIAL ENDING",
      "description": "结局正文",
      "closing": "结局收束语",
      "achievement": "true_tide"
    }
  }
}
```

#### 关键设计点

**1. 三层状态系统**
- `val`（主状态值，0-100）：作品气质的浓缩，命名要"有戏剧张力"（推荐：灼见/缠度/锈蚀/失焦/潮位/炭火），**不建议作为结局主判定**，只做"体验质感调节器"。
- `variables`：自定义状态（道具、关系、知情）。
- `flags`：一次性事件标记，分普通 flag 和 `importantFlag`（触发"重要决定已记录"浮动提示）。

**2. 多类型结局矩阵**
| 类型 | 含义 | 建议数量 |
|------|------|----------|
| TRUE ENDING | 对应原作正文结尾 | 1 |
| NORMAL ENDING | 合理但非最佳 | 1-3 |
| BRANCH ENDING | 关键抉择的长期后果 | 2-4 |
| HIDDEN ENDING | 原作暗示但未展开 | 0-2 |
| SPECIAL ENDING | 彩蛋/元叙事/极端路线 | 0-1 |
| RASH ENDING / BAD ENDING | 错误选项的短结局 | 写作中按需补 |

**结局判定建议**：60-70% 路径驱动、15-25% flag+val 条件、10-15% 稀有组合。**禁止"低 val 直接坏结局"陷阱**。

**3. 节奏与互动**
- 强制规则：**每 1-5 句正文必须给玩家一次互动**（哪怕只是单选项"继续"）
- 超过 8 个 segments 的节点会被 validate.py 警告
- 连续 next 链超过 10 个无互动 → 警告

**4. 场景系统**
- `major` 场景：触发转场动画，连续多节点共用
- `transient` 场景：过场，仅更新场景名

**5. 13 种 ambient + 16 种 effect**
环境氛围（rain/wind/tide/heat/static 等）和瞬间特效（shake/blur/glitch/heartbeat/drown 等）。

### 3.3 validate.py 自动验证脚本

15 项独立检查（**这是整个项目最体现"工程师品味"的部分**）：

| # | 检查项 | 级别 |
|---|--------|------|
| 1 | 基础结构（meta/startNodeId/nodes） | 错误 |
| 2-3 | 引用完整性（节点/成就 ID 全存在） | 错误 |
| 4 | 节点可达性（从 start BFS 遍历） | 警告 |
| 5 | 死胡同（非结局必有 choices/next/routes） | 错误 |
| 6 | 至少一个可达结局 | 错误 |
| 7 | 成就数 > 结局数 | 警告 |
| 8 | routes 必须有 default 兜底 | 错误 |
| 9 | 结局节点必有 title/description/closing | 警告 |
| 10 | 互动节奏（segments ≤ 8） | 警告 |
| 11 | **同向选项 callback 检查**（多选项指向同一节点必须有差异化文本反馈） | 错误 |
| 12 | **选项直跳结局检查**（非草率结局前必须有 closure 节点） | 错误 |
| 13 | progress 范围 0-100 | 错误 |
| 14 | **模板痕迹检查**（禁用"玩家/节点/分支/选项A"等元叙事词，及"把事情推到极端""带着...继续"等 AI 常用模板句） | 错误 |
| 15 | 连续 next 链 ≤ 10 | 警告 |

特别值得关注的是 #14：**显式列出 AI 写作时常见的偷懒套话作为禁用词**，这是把"对抗 AI 模板化"做成了 lint 规则。

### 3.4 剧情游戏启动器（HTML）

单文件 247KB，零依赖、零部署，浏览器直开。功能：

- **书架式 UI**：导入/管理多本剧本、明暗模式切换、字号/动效强度调节
- **沉浸式游玩**：点击/回车推进、回退、自动播放、章节检查点
- **场景转场动画**（仅 major 场景间）
- **存档系统**：自动存档 + 手动存档槽 + 章节检查点（含已解锁的 importantFlag.label 显示）
- **变量驱动 UI**：界面始终显示 variableName 当前值
- **结局/成就追踪**：游玩中累计解锁
- **File System Access API**：Chrome/Edge 可直接绑定本地文件夹做剧本资料库

## 四、最高创作原则（项目哲学）

这是 SKILL.md 中的总纲（罕见地把"创作哲学"提到工程规范同等高度）：

> **每一个选择都必须从当前场景自然长出，每一个后果都必须被世界认真承接，每一个结局都必须在充分变化后以判词收束。**

展开为三条铁律：
1. **自然长出**：选项不是生成器填槽，是此刻这个角色在这个处境下真正可能做的事
2. **世界承接**：选择之后不只改变量，是世界（人物态度/制度反应/物件归处/空间氛围）都被改变
3. **判词收束**：结局页不交代剧情，判词越短前面越要充分

以及反 AI 模板化的具体规则（**选项书写零容忍**）：
- ❌ "说早安，然后声明不会接受分配" → ✅ `"早上好。"`
- ❌ "问他是不是急着搬走" → ✅ `"你要搬走？"`
- ❌ 选项中出现玩家尚未见过的人名/概念
- ❌ "把事情推到极端""带着...继续"等模板句

## 五、实际应用场景

结合用户（人工智能试验场项目）的背景，几个可复用方向：

### 5.1 直接复用：作为 Claude Code Skill

`story-to-game.skill` 是标准的 SKILL.md + references 结构，可直接放到 `.claude/skills/` 下，让 Claude Code 具备"小说改互动游戏"能力。注意原 zip 文件名是 `.skill` 扩展名，需解压后使用 `story-to-game/` 目录。

### 5.2 学习价值：AI 写作工程化的极佳样本

这个仓库是目前看过的 **"对抗 LLM 输出退化"** 最系统的工程实践：
- 把"反偷懒"规则做成可执行 lint（validate.py 第 14 项）
- 用"断点存档 + 记忆重建"硬解长上下文丢失问题
- 用"分批输出 + 章节边界"管理 Token 预算
- 用"确认点 A/B 粒度铁律"防止 AI 过早泄露悬念
- 用"两层规划 + 次级记忆"分离全局与局部上下文

这套方法论可以迁移到任何**长篇结构化创作**场景（技术文档、教程、训练数据合成）。

### 5.3 文档协作场景的参考
与你前面讨论的"多 Agent 协作文档编辑"方案有强关联：
- **互动节奏铁律 = 段落级粒度**：和方案中"段落级 AST"的粒度选择高度一致
- **importantFlag 浮动提示 = rationale 一等公民**：作者标记关键决定的方式与"提案附 rationale"如出一辙
- **结局矩阵的 default 兜底 = routes 必有 default**：避免文档/剧情进入"死胡同"

### 5.4 启动器架构的可借鉴点
- 单文件 HTML + JSON 数据驱动 = **零部署的轻量内容运行时**
- 适合做：教学课件、互动 SOP、面试题库、产品演示脚本
- File System Access API 的本地资料库模式适合做"个人知识库 + 互动浏览"

## 七、独特性与潜在限制

**独特性**：
1. 作者是真正的电影/编剧从业者，规则不是空想，是**对抗 AI 模板化的实战经验**
2. 唯一一个把"反 AI 偷懒"做成 lint 的开源项目
3. JSON Schema 设计与 LLM 写作粒度高度对齐（段落级、节点级）
4. 启动器与技能解耦，可以单独使用任一方

**潜在限制**：
1. 启动器是开发者调试版，UI 不算精致
2. 长篇小说改编对 LLM 上下文要求很高（中长篇必须分批、跨对话）
3. 创作哲学很重，不适合"快速生成轻量游戏"的需求
4. 中文项目，全部规则文档为中文（对非中文使用者不友好）
